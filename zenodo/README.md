# Zenodo Release Workflow

This directory contains the local Zenodo/InvenioRDM release workflow for conda-recipe-upstream-validator.

The goal is to avoid relying only on the automatic GitHub-Zenodo integration. Instead, we create and control a Zenodo draft explicitly before publishing the software release.

This allows us to:

- create a Zenodo draft before the GitHub release is published;
- reserve the version DOI in advance;
- include the DOI in CITATION.cff, the README, and the GitHub release from the beginning;
- upload and validate files explicitly;
- check that local and remote metadata are aligned;
- publish the Zenodo record only after the release artifacts and metadata have been checked.

The workflow is managed by:

```bash
python zenodo/manage.py --help
```

The legacy helper `tools/zenodo_manual_deposit.sh` is no longer used.

## Files

### zenodo/metadata.json

This is the human-edited local source of truth for the Zenodo/InvenioRDM release metadata.

It answers: what do we want to publish?

This file should be committed.

### zenodo/remote.json

This is a generated snapshot of the current remote Zenodo draft or record.

It answers: what does Zenodo currently have?

It is generated by:

```bash
python zenodo/manage.py --refresh-remote
```

It contains:

- base URL;
- version record id;
- concept record id, when available;
- version DOI;
- concept DOI, when available;
- publication state;
- remote timestamps;
- useful links;
- remote file metadata;
- full remote API responses.

Current structure:

```json
{
  "_comment": "Generated by zenodo/manage.py. Do not edit manually.",
  "base_url": "https://sandbox.zenodo.org",
  "record_id": "495196",
  "concept_record_id": "495195",
  "doi": "10.5072/zenodo.495196",
  "concept_doi": null,
  "is_published": false,
  "remote_created": "...",
  "remote_updated": "...",
  "snapshot_updated_at": "...",
  "links": {},
  "remote": {
    "record": {},
    "record_simple": {}
  },
  "files": []
}
```

The two remote representations are:

- remote.record: full draft/record response with `Accept: application/vnd.inveniordm.v1+json`. This is the main representation used for comparison with zenodo/metadata.json.
- remote.record_simple: simplified representation with `Accept: application/json`. Useful for inspection and extracting relations/version parent fields.

zenodo/remote.json is generated state. For sandbox testing, avoid committing it unless there is a deliberate reason to preserve an exact snapshot.

## DOI Model

Zenodo distinguishes between two DOI concepts.

### Version DOI

The version DOI identifies one concrete software release.

Example:

```text
10.5072/zenodo.495196
```

This is the DOI that should normally be used in CITATION.cff for reproducibility.

### Concept DOI

The concept DOI identifies the software project as a whole, across versions.

It points to the version family, normally resolving to the latest version.

In the current sandbox draft, concept DOI may be unavailable in the fetched draft response, so concept_doi can be null.

Zenodo still exposes the parent/concept record id in the simple JSON representation under metadata.relations.version[].parent.pid_value.

For now, the workflow stores concept_record_id and leaves concept_doi as null when unavailable.

## Metadata Representations

### Full metadata

Command:

```bash
python zenodo/manage.py --print-remote-metadata
```

Prints:

- remote.record.metadata

Used for alignment with zenodo/metadata.json.

### Simple metadata

Command:

```bash
python zenodo/manage.py --print-remote-metadata-simple
```

Prints:

- remote.record_simple.metadata

Useful for inspection, not used for metadata roundtrip checks.

## Metadata Comparison

Command:

```bash
python zenodo/manage.py --check-metadata
```

Compares:

- zenodo/metadata.json
- remote.record.metadata

The comparison ignores server-expanded fields added by Zenodo/InvenioRDM, such as:

- resource_type.title
- creators.*.person_or_org.name
- rights.*.title
- rights.*.description
- rights.*.props
- related_identifiers.*.relation_type.title

If such fields are present locally, the helper warns but does not fail.

Expected result before publishing:

```text
Metadata aligned: yes
```

## Relationship with CITATION.cff

Canonical release metadata: zenodo/metadata.json.

Remote DOI state: zenodo/remote.json.

Recommended derivation:

- zenodo/metadata.json title -> CITATION.cff title
- zenodo/metadata.json version -> CITATION.cff version
- zenodo/metadata.json publication_date -> CITATION.cff date-released
- zenodo/metadata.json creators -> CITATION.cff authors
- zenodo/metadata.json description -> CITATION.cff abstract
- zenodo/metadata.json rights[0].id -> CITATION.cff license
- zenodo/metadata.json subjects -> CITATION.cff keywords
- zenodo/remote.json doi -> CITATION.cff identifiers[type=doi].value

CITATION.cff should normally use the version DOI (not concept DOI).

## Release Branch Workflow

Rule: the release DOI must enter the repository before the Git tag is created.

1. Work on development branch.
2. Create release branch (example: release/0.1.1).
3. Freeze release metadata in zenodo/metadata.json and related release files.
4. Create or update Zenodo draft (`--init`, `--metadata`, `--refresh-remote`, `--status`).
5. Check alignment (`--check-metadata`).
6. Generate/update CITATION.cff from zenodo/metadata.json + zenodo/remote.json.
7. Commit release preparation files.
8. Merge into main.
9. Create Git tag only after DOI/citation metadata are committed.
10. Build release artifacts from the tag.
11. Upload files (`--files`), refresh, re-check.
12. Publish (`--publish`), refresh and re-check status.
13. Create GitHub release including Zenodo version DOI.
14. Merge main back into development.

## Normal Commands

```bash
# Create draft (first time)
python zenodo/manage.py --init

# Push metadata
python zenodo/manage.py --metadata

# Upload files
python zenodo/manage.py --files

# Refresh local remote snapshot
python zenodo/manage.py --refresh-remote

# Show status
python zenodo/manage.py --status

# Print local metadata
python zenodo/manage.py --print-local-metadata | jq .

# Print full remote metadata
python zenodo/manage.py --print-remote-metadata | jq .

# Print simple remote metadata
python zenodo/manage.py --print-remote-metadata-simple | jq .

# Check alignment
python zenodo/manage.py --check-metadata

# Publish
python zenodo/manage.py --publish
```

## Sanity Check

```bash
jq '{
  record_id,
  concept_record_id,
  doi,
  concept_doi,
  is_published,
  remote_created,
  remote_updated,
  snapshot_updated_at,
  has_record: (.remote.record != null),
  has_record_simple: (.remote.record_simple != null),
  files_count: (.files | length)
}' zenodo/remote.json
```

## Notes About Sandbox

Sandbox DOIs look like:

```text
10.5072/zenodo.xxxxxx
```

They are not production DOIs. Do not treat sandbox DOI state as final release DOI.
